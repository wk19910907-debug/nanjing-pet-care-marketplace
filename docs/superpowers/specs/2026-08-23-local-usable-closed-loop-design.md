# 南京宠物上门服务本地可用闭环设计

## 目标

把现有通过测试但缺少直接运行入口的工程，补齐为普通用户在一台电脑上即可操作的产品。第一阶段完成浏览器网页，第二阶段完成可导入微信开发者工具的小程序。两端都覆盖“宠主下单、平台匹配服务人员、服务人员履约、宠主确认”的最小闭环。

## 方案选择

采用本地体验模式作为当前交付：不要求 Docker、短信、微信支付、对象存储或公网资质；启动后提供宠主、服务人员、运营三个预置身份，业务数据保存在浏览器本地。现有 Fastify、Prisma 和领域测试保留为后续生产化基础。

未采用的方案：直接连接 PostgreSQL 的双进程开发环境更接近生产，但启动和维护成本高；直接发布公网或正式微信小程序需要域名、备案、AppID、支付商户号等外部资质，无法作为无需额外输入的本地交付。

## 网页端

在现有 React/Vite 运营端中加入统一产品壳和角色切换：

- 宠主：填写服务类型、宠物、区域、详细地址、上门时间和备注，查看价格并提交订单；查看订单状态和服务报告；确认完成。
- 运营：查看待匹配订单，选择已认证服务人员并派单。
- 服务人员：查看自己的任务，开始服务，勾选履约清单，填写文字记录并提交服务报告。
- 数据：订单和操作记录存入 `localStorage`，刷新页面后仍保留；提供“恢复体验数据”能力。

订单状态固定为 `待匹配 → 待服务 → 服务中 → 待确认 → 已完成`。网页只允许与当前状态相符的操作，关键操作显示中文反馈。

## 微信小程序端

保留现有页面结构，增加体验模式数据仓库和首页角色入口。小程序使用 `wx.setStorageSync` 持久化同一业务状态机，覆盖宠主下单、运营派单、服务人员履约和宠主确认。增加 `project.config.json`，允许使用游客 AppID 导入微信开发者工具进行本地体验。

小程序与网页在本地体验阶段不共享数据；正式上线时二者共同连接现有 API。

## 启动与交付

根目录提供 `pnpm dev` 启动网页，默认地址 `http://127.0.0.1:43123`。README 给出首次安装、启动、角色操作顺序和微信开发者工具导入路径。默认数据包含两名已认证服务人员，宠主可自行创建新订单。

## 错误处理与安全边界

- 必填字段缺失时不创建订单，并在表单附近显示错误。
- 无可用服务人员时保持待匹配状态。
- 履约清单或服务记录不完整时不允许提交报告。
- 本地体验数据不得包含真实手机号、门锁密码、支付凭据或精确住址。
- 本地体验明确标记为演示模式，不声称已完成真实支付、短信验证、微信审核或生产部署。

## 验收

- 自动化单元测试验证状态转换、持久化和非法操作。
- Playwright 从宠主下单开始，依次切换运营、服务人员和宠主，最终看到订单“已完成”。
- `pnpm check`、网页构建和小程序 TypeScript 检查全部通过。
- 在新终端执行 README 命令后，网页可打开并完成闭环；小程序目录可被微信开发者工具导入。
