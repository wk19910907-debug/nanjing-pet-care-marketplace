# 小程序最少资料衔接

延续用户要求直接执行、少填写、不反复询问的既定方向，本轮只解决首次昵称与会话校验，不扩大为完整生产登录系统。

## 方案

选择在现有宠主预约页和服务人员任务页内展示一个昵称输入框；保存成功后重读会话再继续原流程。单独注册向导会增加跳转，自动生成昵称则不能表达用户意愿，均不采用。昵称使用后台现有校验，禁止联系方式，客户端只做长度/空值预检。

新增共享 access 服务读取后台当前会话。只有明确 HTTP 401 才清除失效令牌并发起一次登录；网络错误和权限拒绝不触发重新登录。开发模式允许使用仅回环本地登录切换目标角色，不向开发后端发送缓存的正式 Bearer。正式模式身份完全由后台返回，角色不符时提示，不靠页面参数提升权限。同角色并发读取合并；不同角色并发请求拒绝，避免本地 Cookie 切换竞态。

资料保存后不信任 PATCH 的成功状态，重新读会话确认昵称非空且身份一致，再读取订单/预约数据。等待请求时禁止重复提交，页面卸载后不更新 UI。页面失败保留已输入昵称；刷新/重开使用已保存资料，不要求重复填写。

## 范围与验收

不改变后台权限、邀请码、注册方式、宠主字段、支付或审核规则。服务人员申请与审核仍在网站后台衔接；宠主没有宠物/地址资料的原生新增流程不在本轮。微信生产会话交换路由在当前后端尚不存在，是后续实现事项，不得描述为只差凭据。

测试覆盖：401 一次恢复、网络错误不登录、错误角色不放行、并发锁、开发 Bearer 隔离、昵称 PATCH 仅发送昵称、保存失败/不明响应不进入业务、两个实际 Page 首次资料门槛、构建和既有履约回归。自动化不代替真机验证。
