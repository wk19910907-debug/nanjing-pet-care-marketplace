# 原生首次预约资料闭环

用户要求：可正常使用、少填写、不反复询问，先完成喂猫/遛狗预约。因此直接沿用既有服务范围和定价，不重新征询方案选择。

采用预约页内添加资料，比跳到独立资料管理页少一次切换，也避免后台代填。宠物仅必填名字，物种跟随当前服务；地址只选已开放南京行政区、填详细地址，不收门锁密码、经纬度或额外联系方式。已有资料可直接选择，多个地址展示宠主本人的详细门牌以便区分。宠物注意事项可选并折叠，不要求繁琐档案。

日期/时间使用原生 picker，以明确北京时间 +08:00 合成 startsAt；只允许有效且未来时间。选择变更立即取消旧报价，报价或提交时冻结输入、阻止重复点击。提交使用本次报价对应的快照；提交结果不明时保持同一订单幂等键与冻结输入，允许重试，不能悄悄创建另一单。

资料使用现有已鉴权 POST /api/v1/pets 和 /api/v1/addresses，增加可选 clientRequestId（1–100位ASCII字母数字/下划线/横线）以及数据库按 ownerId/key 唯一约束。相同键相同资料返回原记录；相同键不同资料409 PROFILE_REQUEST_CONFLICT；不同宠主同键互不影响。未携带键的旧网站行为兼容。详细地址继续加密存储，仅宠主本人列表可以读取自己的detail，绝不带门禁指令、密文或他人资料。只加nullable字段和唯一索引，不删除原资料。

页面保存操作成功后加入后端返回的资料并自动选择。失败保留草稿；不明结果保留该保存快照与键、冻结对应编辑，重试沿用。页面卸载后不再setData/Toast/跳转。不在本地持久化敏感地址草稿。

地址坐标暂沿用既有试点行政区中心点，不假装是真实定位或精确里程；价格与匹配仍由后台控制。微信真机、公开HTTPS API及小程序发布不在本次验收范围。

验证：真实临时PostgreSQL幂等/并发/冲突/隔离/加密测试；客户端API契约；空资料首次预约、失败恢复、重复点击、报价失效、未知订单结果与页面卸载测试；全部原生入口构建、模板绑定检查；全仓回归和独立复核。
