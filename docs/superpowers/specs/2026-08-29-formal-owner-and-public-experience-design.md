# 正式运营风格的公开官网与宠主端设计

日期：2026-08-29

## 决策结论

采用用户确认的 A「可信服务型」视觉方向，同时改造公开官网与登录后的宠主端。产品的第一转化目标是让南京宠主快速提交“上门喂猫”或“上门遛狗”预约，由平台匹配合适的已审核服务人员。

本次是正式运营界面与信息架构升级，不把尚未接入的能力包装成已经存在。不得声称已支持在线支付、保险、客服热线、全南京覆盖或已积累特定数量的服务人员和订单。

## 产品边界

- 保留当前真实数据库、认证、服务端报价、订单匹配和履约状态机。
- 宠主只能提交订单和查看状态，不能自行挑选服务人员。
- 首期服务只包含上门喂猫与上门遛狗。
- 公开官网无需登录即可浏览，点击预约后进入现有身份入口或已登录宠主端。
- 服务人员端、管理员端只做必要的导航兼容，不在本次重做视觉与流程。
- 当前未接入在线支付、微信二维码和公开手机号，因此不展示相关承诺或不可用入口。

## 视觉语言

- 品牌继续使用“南京安心宠”，不复制参考产品的品牌、人物、插画或文案。
- 主色为温暖珊瑚红，背景使用暖白与浅米色，正文使用深棕灰；强调色只用于主要预约动作和当前状态。
- 圆角、柔和阴影和少量宠物图形建立亲和感，但避免儿童化、装饰堆叠和过多彩色标签。
- 桌面端内容最大宽度约 1180px；移动端以 390px 为主要验收宽度。
- 正文不小于 14px，关键按钮高度不小于 44px；状态不能只依赖颜色表达。

## 公开官网

### 顶部导航

- 左侧品牌与“南京”服务城市。
- 右侧只保留真实可用入口：服务介绍、服务保障、常见问题、登录。
- 桌面端固定显示“立即预约”主按钮；移动端使用简化顶栏和明显的首屏按钮。

### 首屏

- 主标题：出门放心，宠物在家也被认真照顾。
- 副标题：南京上门喂猫、上门遛狗服务，提交需求后由平台匹配合适的服务人员。
- 主按钮：立即预约。
- 次按钮：了解服务流程。
- 首屏同时展示三项真实流程能力：身份审核、平台匹配、服务留痕。
- 页面不再以“体验”“工作区”“技术演示”作为首屏主信息；尚未正式开放的边界放在预约确认和常见问题中如实说明。

### 服务与价格

- 上门喂猫：¥32 起；喂食换水、猫砂清理、宠物状态反馈。
- 上门遛狗：¥37 起；牵引散步、饮水照看、服务状态反馈。
- 服务卡可直接预选对应服务并进入预约。
- “起”字必须保留，最终价格继续由服务端根据现有规则生成。

### 服务流程与保障

服务流程为四步：提交预约、平台匹配、上门服务、查看记录。

保障区只描述已存在或当前产品能够兑现的机制：

- 身份资料审核。
- 平台统一匹配。
- 订单状态可查。
- 服务过程留痕。

不展示虚假的保险金额、赔付承诺、服务次数或用户评价。

### 常见问题与页脚

- 解释覆盖区域、报价方式、匹配方式、如何查看服务进度以及当前支付方式。
- 未正式开通的区域明确提示提交后需由平台确认，不声称南京全域即时接单。
- 页脚保留品牌、服务范围、隐私与安全提醒，不显示空白联系方式。

## 宠主端

### 全局结构

- 顶栏显示品牌、南京、当前宠主和退出入口。
- 移动端底部导航只保留“首页、订单、我的”三个真实入口。
- 移除“工作区、刷新全部、本地试运营”等内部或测试语气。
- 首页只承担发现服务、快速预约和查看最近订单三项任务。

### 首页首屏

- 问候标题：今天需要照顾谁？
- 辅助说明：提交需求，平台为你匹配合适的服务人员。
- 两张主要服务卡并列或在移动端纵向排列，显示服务内容与起步价。
- 主按钮“立即预约”始终清晰可见；从服务卡进入时自动预选服务。
- 信任条紧随服务卡，显示“身份审核、服务留痕、平台匹配”。

### 轻量预约流程

预约压缩为三个用户可理解的阶段，底层仍复用现有宠物、地址、报价和下单 API：

1. 选服务与时间：选择上门喂猫或遛狗、日期、时间和允许的服务时长。
2. 填上门信息：选择已有宠物与地址；没有资料时在当前步骤内快速补充。首次新增只要求宠物昵称、类型、所在区和详细地址，备注保持选填折叠。
3. 确认预约：展示服务、时间、宠物、地址摘要和服务端报价，用户确认后提交。

南京固定显示，不要求重复输入。返回上一步不清空草稿；提交失败保留全部已填信息。所有必填校验在当前步骤就地显示，不弹出技术错误。

### 订单状态

- 首页最多展示一张最近活动订单卡；全部历史进入订单页。
- 状态卡用普通语言说明“当前状态”和“接下来会发生什么”。
- 匹配前显示平台处理中；匹配后显示服务人员公开信息；履约中显示进度；完成后显示服务记录和确认入口。
- 精确地址、内部 ID、数据库字段和鉴权信息不得出现在列表摘要中。

### 我的

- 显示宠主昵称、宠物资料、常用地址与安全提示。
- 编辑宠物和地址作为二级动作，不在首页展示完整表单。
- 当前没有手机号、微信二维码或支付账户时，不显示伪造字段和空卡片。

## 组件与数据边界

- `PublicLanding` 负责公开官网静态内容、服务预选和进入预约，不读写订单状态。
- `PilotApp` 继续管理登录身份和真实角色路由，移除面向用户的试运营标签。
- `OwnerHome` 负责编排宠主首页、活动订单和预约入口。
- `BookingFlow` 管理三阶段预约草稿；网络访问继续由现有 API 客户端承担。
- 价格、认证、匹配和订单状态只能使用服务端返回值，不在前端伪造。
- 公开官网选择服务后只传递服务类型；用户登录后再补充受保护的宠物与地址信息。

## 错误、空状态与安全

- 首屏加载失败时保留品牌和可重试入口，不展示空白页。
- 报价失效时回到确认阶段重新获取，不自动提交旧价格。
- 重复点击提交时禁用按钮，依赖现有服务端幂等保护。
- 无宠物、无地址和无订单时使用行动文案引导补充，不出现内部数据模型术语。
- 不索取门锁密码；上门说明提示不要填写敏感凭据。
- 不因正式运营视觉而隐藏真实的服务范围、报价和付款限制。

## 响应式与可访问性

- 390×844 无横向滚动，主按钮在首屏和预约底部易于触达。
- 1280×800 下官网与宠主端不过度拉伸，卡片保持明确主次。
- 键盘可访问全部链接、按钮、表单和步骤导航。
- 表单错误与状态更新使用可读文本，保证屏幕阅读器能够理解。
- `prefers-reduced-motion` 下关闭非必要动画。

## 验收标准

- 访客在首屏能回答：提供什么服务、参考价格、由谁匹配、如何开始预约。
- 官网的服务卡和主按钮均可进入真实登录/预约链路。
- 宠主能在三阶段内完成“服务与时间 → 上门信息 → 报价确认 → 提交订单”。
- 已有宠物和地址可直接复用，首次用户可在流程内快速新增。
- 下单后首页显示真实活动订单，管理员匹配、服务人员履约与宠主确认链路不回归。
- 页面不出现“本地试运营、工作区、刷新全部”等内部文案。
- 页面不声称具备在线支付、保险、客服电话或虚构运营数据。
- 组件测试、类型检查、生产构建和核心浏览器闭环全部通过。

## 非目标

- 不新增自主选服务人员、即时聊天、社区、商城、优惠券或会员体系。
- 不接入在线支付、短信、地图、微信登录或新的第三方服务。
- 不重构服务人员端和管理员端业务流程。
- 不改变现有报价规则、匹配规则和履约状态机。
