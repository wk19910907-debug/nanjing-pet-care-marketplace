# 宠主端轻量服务首页设计

日期：2026-08-28

## 目标

把当前“宠主工作区”从一次性展示宠物档案、服务地址、报价和订单的业务表单，改造成普通宠主容易理解的移动端服务首页。用户先了解服务、价格和保障，再通过渐进式步骤完成预约。

本次只改宠主端的信息架构与交互表现，不修改服务人员端、平台管理员端、认证机制、报价规则、派单规则或履约状态机。

## 成功标准

- 宠主进入首页时看不到空白档案表单或技术性工作区文案。
- 首屏能在数秒内回答：提供什么服务、参考价格、如何预约、平台如何保障。
- 首次下单不要求用户预先理解“宠物档案”和“服务地址”的系统概念。
- 一次只展示一个决策阶段；非必要字段默认隐藏。
- 城市固定为南京，不要求重复填写。
- 提交后仍由平台匹配服务人员，不提供自主挑选服务人员的入口。
- 已有 API、权限边界、服务端报价和真实订单闭环继续工作。
- 390×844 手机视口无横向滚动，主要按钮触控高度不低于 44px；桌面端保持可用。

## 视觉与内容原则

参考视频和截图的优点仅用于提炼信息层级，不复制其品牌、人物、插画或原文案。

- 使用面向消费者的服务首页，而不是后台控制台布局。
- 保留当前“南京安心宠”品牌，使用温暖、可信、克制的视觉语气。
- 首屏以服务卡和明确行动按钮为主，减少说明性长段落。
- 用图形化服务入口、短文案、价格和状态卡建立扫描节奏。
- 不增加与首版闭环无关的搜索、商城、社区、消息或自主选人功能。

## 页面结构

### 1. 顶部栏

- 品牌：南京安心宠。
- 城市：南京。
- 右侧提供“我的订单”入口和当前宠主昵称。
- 移除“宠主工作区”“刷新全部”等面向内部人员的表达；刷新作为订单区域中的次要操作保留。

### 2. 首屏服务区

- 主标题：放心把它交给我们。
- 辅助说明：上门喂猫、上门遛狗，由平台匹配已认证服务人员。
- 两张主要服务卡：
  - 上门喂猫，¥32 起；喂食换水、清洁宠物区域、提交服务记录。
  - 上门遛狗，¥37 起；牵引散步、饮水照看、提交服务记录。
- 每张卡均可进入预约流程；首屏另保留一个统一“立即预约”主按钮。

### 3. 信任保障区

展示四个短入口，不创建额外复杂页面：

- 人员认证
- 平台匹配
- 服务留痕
- 异常协助

每项附一行简短解释；不得使用无法兑现的保险、血统或背景调查承诺。

### 4. 当前订单区

- 无订单时展示简短空状态和预约按钮。
- 有订单时只展示最近一笔活动订单：服务类型、宠物、预约时间、当前状态和下一步动作。
- 用户可展开或进入“全部订单”查看历史记录。
- 订单已经进入履约阶段时，首页优先展示订单进度，而不是再次展示预约表单。

### 5. 移动端底部导航

首版只提供三个真实入口：

- 首页
- 订单
- 我的

不放置尚未实现的社区、消息或商城入口。桌面端改为顶部或侧边的等价导航，不强制模拟手机外壳。

## 渐进式预约流程

预约使用单一流程容器，不再要求用户先分别创建档案和地址。

### 第一步：选择服务

- 上门喂猫或上门遛狗。
- 默认使用用户从服务卡进入时选择的服务。
- 同时展示起步价和服务内容。

### 第二步：选择时间

- 预约日期与时间。
- 服务时长只显示当前服务允许的选项，提供清晰默认值。
- 当前已有报价约束继续由服务端校验。

### 第三步：宠物信息

- 必填：宠物昵称、宠物类型。
- “照护备注”作为选填折叠项。
- 如果已有宠物，优先提供已有宠物快捷选择，并允许新增。
- 新增宠物时复用现有创建宠物 API；用户不需要感知“先建档再下单”。

### 第四步：上门信息与确认

- 城市固定显示为南京市，不提供输入框。
- 必填：服务区、详细服务地址。
- “特殊上门说明”作为选填折叠项；不索取门锁密码等超出当前安全边界的信息。
- 如果已有地址，优先提供已有地址快捷选择，并允许新增。
- 新增地址时复用现有创建地址 API。
- 地址准备完成后获取服务端报价，展示价格明细与“不在此页面收取线上支付”的现有试运营说明，再由用户确认提交订单。

每一步支持返回；未完成当前必填项时不可进入下一步。返回不会清空已经填写的内容。

## 组件边界

- `OwnerHome`：负责首页编排、服务入口和活动订单摘要。
- `ServiceCard`：只展示一种服务的名称、价格、内容和预约动作。
- `TrustHighlights`：只展示四项平台保障说明。
- `ActiveOrderCard`：只展示最近活动订单及对应下一步动作。
- `BookingFlow`：维护预约步骤与草稿，不直接实现网络请求。
- `PetStep`、`ScheduleStep`、`AddressStep`、`QuoteStep`：分别负责单一阶段的输入与校验。
- 现有 API 客户端继续负责宠物、地址、报价和订单请求；不得在展示组件中复制鉴权或报价逻辑。

组件可根据现有代码规模合并，但业务职责必须保持上述边界，避免再次形成一个巨型工作区组件。

## 数据流

1. 宠主首页加载已有宠物、地址和订单。
2. 用户从服务卡启动预约，创建仅存于客户端的预约草稿。
3. 用户选择已有宠物和地址，或在对应步骤调用现有 API 创建新记录。
4. 所有必需引用和时间准备完成后，客户端调用现有服务端报价接口。
5. 用户确认报价后调用现有创建订单接口。
6. 成功后关闭预约流程、刷新订单，并把活动订单卡置于首页主要位置。
7. 后续匹配、履约、报告与确认继续使用现有订单状态和接口。

不得在浏览器本地伪造价格、认证状态或订单状态。

## 错误与空状态

- 页面级加载失败：保留页面骨架并提供“重新加载”，不清空已填写草稿。
- 创建宠物或地址失败：错误显示在当前步骤，用户可直接重试。
- 报价失效或服务端拒绝：返回确认步骤，说明需要重新获取报价。
- 创建订单失败：保留已完成草稿，不重复创建宠物或地址。
- 无宠物、无地址、无订单均使用普通用户能理解的行动文案，不展示内部数据模型名称。
- 网络请求期间禁用重复提交；继续依赖现有服务端幂等与鉴权保护。

## 测试与验收

### 组件与单元测试

- 服务卡选择能正确预填服务类型。
- 预约步骤只在当前必填项有效时前进。
- 已有宠物和地址可直接选择；新记录只创建一次。
- 非必填备注保持可折叠，且不阻塞预约。
- 报价必须来自服务端；未取得报价不能提交订单。
- 下单成功后出现活动订单卡，预约流程关闭。
- 不同订单状态显示正确的下一步动作。

### 浏览器验收

- 未登录入口和宠主身份直达继续工作。
- 390×844 下首屏没有空表单、无横向溢出、主要按钮不小于 44px。
- 1280×800 下内容不过度拉伸，仍保持清晰的主次层级。
- 完成“选择服务 → 时间 → 宠物 → 地址 → 报价 → 提交订单”。
- 平台管理员仍能匹配订单，服务人员仍能履约，宠主仍能查看证据并确认完成。
- 刷新页面后真实服务器订单保持存在；错误状态不泄露精确地址或内部凭据。

## 非目标

- 不新增搜索、社区、商城、消息中心、会员体系或优惠券。
- 不开放宠主自主选择服务人员。
- 不修改服务人员申请、平台审核、派单、履约证据或结算规则。
- 不新增线上支付、手机号或微信二维码采集。
- 不照搬参考产品的品牌、插画、人物资料或推荐人员内容。
