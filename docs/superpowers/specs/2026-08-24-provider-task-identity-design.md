# 服务人员任务身份闭环设计

## 背景

公开体验已经支持服务人员申请、平台审核和按区域与服务类型匹配。线上验收暴露出下一处断点：订单可以匹配给新审核人员，但服务人员工作区仍由 `DemoApp` 固定传入 `provider-wang`，因此新人员无法在自己的视角看到并履约该订单。

本阶段只补齐浏览器本地体验中的服务人员身份与任务闭环，不引入真实登录、联系方式、身份材料或服务端会话。

## 目标

- 服务人员工作区可以选择任一已认证体验人员，并只显示该人员的订单。
- 平台刚完成匹配后，进入服务人员视角时默认展示被匹配人员。
- 页面刷新后，优先展示拥有最新进行中任务的已认证人员；没有进行中任务时回退到王小宁，再回退到首个已认证人员。
- 服务人员只能开始和提交分配给自己的订单；领域函数必须校验人员身份，不能只依赖 UI 过滤。
- 新审核人员可以从匹配、开始服务、提交报告到宠主确认完成同一订单。
- 保持现有 version-1 浏览器状态、种子数据、报价、订单、审核和恢复体验行为兼容。

## 非目标

- 不创建真实账号、密码、手机号、微信登录、验证码或 OAuth。
- 不收集真实姓名、身份证、证件照片、背景调查、合同、银行卡或支付信息。
- 不实现生产权限系统、服务端会话、人员下线或排班。
- 不改变价格、南京体验区域、平台匹配资格或订单状态机。
- 不在本阶段拆分喂猫与遛狗的履约清单文案。

## 方案比较

### 方案 A：已认证人员选择器，并自动选中最近匹配人员（采用）

在服务人员工作区顶部显示已认证体验身份选择器。平台匹配成功时把本次人员设为当前体验身份；刷新时通过订单状态推导默认身份。该方案显式、可测试，支持多个申请人，同时保持浏览器本地边界。

### 方案 B：始终显示最新审核人员

实现简单，但当存在多个申请人或种子人员时会隐藏其他人的任务，也无法解释为什么身份自动变化，因此不采用。

### 方案 C：真实登录或邀请码

更接近生产系统，但会引入账号、联系方式、认证服务和隐私合规，超出当前安全体验范围，因此不采用。

## 领域接口

新增纯函数：

```ts
export function preferredProviderId(state: DemoState, requestedProviderId?: string): string | undefined
```

选择顺序：

1. `requestedProviderId` 存在于 `state.providers` 时返回它；
2. 从订单尾部向前查找状态为 `WAITING_SERVICE`、`IN_SERVICE` 或 `WAITING_CONFIRMATION` 且人员仍存在的订单，返回其 `providerId`；
3. 返回 `provider-wang`（若存在）；
4. 返回第一个已认证人员；
5. 没有人员时返回 `undefined`。

修改履约接口，把人员身份作为必填参数：

```ts
export function startService(state: DemoState, orderId: string, providerId: string): DemoState
export function submitReport(state: DemoState, orderId: string, providerId: string, report: ServiceReport): DemoState
```

两个函数先验证人员存在且已认证，再验证 `order.providerId === providerId`。不匹配时抛出 `只能操作分配给自己的订单`，且不得修改订单或审计记录。原有状态检查和完整清单检查保持不变。

## UI 组件与状态

`DemoApp` 新增 `selectedProviderId` 状态：

- 初始值使用 `preferredProviderId(initialState)`；
- 平台匹配成功后设置为本次匹配的 `providerId`；
- 进入服务人员视角前再次用 `preferredProviderId(state, selectedProviderId)` 规范化，避免指向已不存在的人员；
- 刷新后不新增独立 localStorage 字段，而是从已经持久化的进行中订单推导。

`ProviderWorkspace` 接收当前人员 ID 和身份切换回调。顶部显示“体验服务人员身份”选择器，选项格式为 `姓名 · 区域 · 已认证`。选择器只使用 `state.providers` 中的已认证人员。

当前身份摘要动态展示姓名、区域与服务能力。任务列表只过滤 `order.providerId === selectedProviderId`。没有可用人员时显示安全空状态，不渲染开始服务或提交报告按钮。

开始服务和提交报告回调都携带当前人员 ID。按钮事件不得从订单对象反推或替换人员身份。

## 数据流

1. 服务人员申请并由平台审核，生成带显式 `providerId` 的已认证人员。
2. 宠主提交订单；平台仅从区域和服务能力均匹配的已认证人员中选择。
3. 匹配成功后，`DemoApp` 保存新状态并把被匹配人员设为当前体验身份。
4. 切换到服务人员视角，选择器显示该人员，工作区只显示其订单。
5. 开始服务和提交报告时，领域层同时验证订单状态与人员归属。
6. 宠主确认后订单完成；刷新时若没有其他进行中任务，默认身份回退到王小宁，但用户仍可在选择器中查看新人员的已完成任务。

## 错误与兼容性

- 选择了不存在的人员 ID 时，由 `preferredProviderId` 安全回退，不产生崩溃。
- 直接调用领域函数尝试操作其他人员订单时失败关闭，不产生审计记录。
- 旧 v1 状态无须迁移；当前人员身份为派生 UI 状态，不写入业务状态。
- 固定种子人员与已审核申请的安全重建逻辑保持不变。
- 原有王小宁完整闭环测试继续通过，调用点仅增加显式 `providerId`。

## 响应式与可访问性

- 身份选择器有明确可访问标签，选择框和操作按钮高度不低于 44px。
- 390×844 手机宽度下，身份选择器、摘要和任务卡纵向排列且文档无横向溢出。
- 1440×900 桌面宽度下，身份摘要保持清晰，履约任务不被申请面板挤压。
- 身份变化后可见标题与任务内容同步更新，避免仅通过颜色表达当前身份。

## 测试与验收

### 单元测试

- `preferredProviderId` 尊重有效显式选择。
- 无显式选择时优先最新进行中订单的人员。
- 无进行中任务时回退王小宁；人员数组为空时返回 `undefined`。
- 王小宁不能开始或提交新审核人员的订单，失败后订单和审计不变。
- 正确人员可以完成开始服务和提交报告，原状态校验仍有效。

### 浏览器测试

- 申请“体验小林”并审核，创建秦淮区遛狗订单，匹配后进入服务人员视角自动显示体验小林和该订单。
- 切换到王小宁时看不到体验小林的订单；切回后可完成履约报告，宠主可确认完成。
- 页面刷新后，进行中的体验小林订单仍决定默认身份。
- 手机与桌面 populated 状态无横向溢出，身份选择器及主要按钮不低于 44px。
